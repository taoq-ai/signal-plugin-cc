**Verdict: FIX.** The arch review of leave-digest at d46d75e found two blocking problems. The suite passes (108 tests OK on a `git archive` copy), but both problems only show with real files or real timing.

**Blocking**
1. **The "no longer listens" answer is lost in production** (`signal_cc/adapters/files.py:158`, high). A session taken over at the Mac writes `gone` into its gather entry, then its listener exits. From then on `entries()` sees a dead pid and deletes the file, so the "gone" marker is lost every time, not just in a race.
   - A tag or a poll pick of that session now gets silence, which breaks acceptance 5.
   - When an older prompt outside the digest is waiting, the old "Which prompt?" hint comes back.
   - I reproduced this across real processes; the same setup with the pid alive gives the correct answer.
   - The tests miss it because the fake gathering has no pid.
   - Fix: keep a `gone` entry even when its pid is dead (`if row.get("gone") or alive(...)`), and add an adapter test where the `gone` entry was written by a child process that has exited.
2. **A session that found the owner away can still end up in a digest** (`signal_cc/app/conversation.py:61`, medium; new in this round). Such a session enters the shared list with `sent` empty and only records it after its own send finishes. If a lead reads the list while that send is in flight, the session is listed in the digest and poll and also sends its own message. Picking it in the poll then gets silence. This happened in 3 of 3 runs with a 0.5 s send.
   - Fix: send first, then enter with `sent` already set, or mark the entry so the lead never takes it.

**Closed from round 1**
- Only sessions that waited at the Mac join a digest.
- A poll pick of a taken-over session is answered, and a tag gets one answer — but only in the logic and the fake harness. Finding 1 breaks both again in production.
- Cleanup of finished or killed entries is tested.
- The digest poll is closed by the last member only.
- An OSError from the poll send is caught.
- Gathering is documented in `ports.py` and the README table.

**Mutants:** 7 of 8 killed. `len(picked) != 1` weakened to `not picked` survived in two fresh copies; a single-choice poll never sends two picks, so it doesn't block.

**PR #14 (listener-lifetime).** A trial merge (`git merge-tree d46d75e 2227f93`) conflicts in README.md, `conversation.py`, `routing.py`, `tests/test_adapters.py` and `tests/test_domain.py`. `wiring.py` merges cleanly, contrary to the brief. Neither hazard below is a defect at this head, but this PR should fix both now:
- **Lost message.** #14 fills `sent` with the session's earlier timestamps before sending, so this PR's `if not sent:` is false after the merge. A session with earlier kept messages would then never send its finished turn. #14's `keep(self.session, tag, ts)` also lands where `ts` is undefined on the digest path, which invites binding it to the digest's timestamp. The fix:
  - `_gather` returns the digest explicitly.
  - Branch on `if not joined:` instead of `if not sent:`.
  - Name the session's own message timestamp `own`, set to `None` when it went out in a digest, so the merge becomes `if thread and own is not None: keep(...)`.
  - The digest's text and poll timestamps are then never kept.
- **Shifted arguments.** Both PRs add a sixth positional parameter to `route()` and pass it positionally, so a merged signature could shift #14's `mine` into `gone` and `kept` into `mine`. Replies tagged for another session would then reach this one. Make `gone` keyword-only (`*, gone=()`) and call it as `gone=gone`.
- **Order inside `route()`** for whichever PR merges second:
  1. live tag;
  2. #14's `mine` (Take);
  3. this PR's digest-member block and gone check;
  4. #14's `kept` (SKIP);
  5. quotes.

  The gone check has to come before `kept`, or a session being forgotten while it is stopped would suppress the "no longer listens" answer.
