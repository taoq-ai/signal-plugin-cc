**Why not the manifest at 0.3.0:** I read the release-please code bundled in action v4.4.1. A manifest version other than `0.0.0`, with no matching tag, is treated as the last release and bumped from. With 0.3.0 in the manifest and a bootstrap-sha, the feat commits in the history would push the first release PR to 0.4.0.

**What I set instead:**
- The manifest is `{".": "0.0.0"}`, which the code treats as "no release yet", plus `initial-version: "0.3.0"`. The first release PR proposes 0.3.0 and sets the manifest to 0.3.0. `initial-version` has no effect once a release exists, so nothing needs removing later.
- I rejected the two other routes as more fragile: a `release-as` config entry needs a follow-up PR to remove it, and a `Release-As:` footer depends on the squash message.
- `bootstrap-sha` is `fbc44e1` (#2, where plugin.json went to 0.2.0), not the current main. The v0.3.0 changelog then lists #3 to #7 plus this PR. With the current main, a run after a `chore:` merge would find nothing to release, and v0.3.0 would wait for an unrelated feat.

**Workflow:** the action is pinned to `5c625bfb5d1ff62eadeeb3772007f7f66fdcf071`, which is v4.4.1, where `v4^{}` points according to `git ls-remote`. It runs on push to main. The workflow-level permissions are `{}`, and only the job gets `contents: write` and `pull-requests: write`. Other settings: release-type `simple`, `bump-minor-pre-major`, `include-component-in-tag: false` so tags read `v0.3.0`, and extra-files updates `$.version` in `.claude-plugin/plugin.json`. `tests.yml` is unchanged.
